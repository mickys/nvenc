# T15: GTX 1650 (Turing TU117), 2026-10-20

The RTX 4090 left the machine for an ASUS Phoenix GTX 1650 OC 4 GB (TU117). Its NVENC is version 6.6 (class 0xb4b7, the
Volta generation), its NVDEC class 0xc4b0, the host classes c46f (channel) / c461 (usermode). NullMoth 2.4.3 runs it
(display, Metal 3) but its own encoders do not register on it.

## T15.01: classes from the GPU

`rm_class(rm, RM_CLS_NVENC | _NVDEC | _CHANNEL | _USERMODE)` reads `NV0080_CTRL_CMD_GPU_GET_CLASSLIST_V2` once and picks
the first class the GPU has from Ada's down to Volta's. Every encoder, decoder and tool uses it; the NVENC setup magic is
`(class << 16) | 6` (0xB4B70006 on NVENC 6.6). The setup structures are the same as on Ada.

## T15.02: HEVC encode on NVENC 6.6

Our HEVC encode faulted (MMU) on the second P picture. The fourth trace of NVIDIA's Linux driver (user-approved,
`docs/traces/gtx1650-linux`) showed:
- references are given by **DPB slot**, as for H.264: `l0[0]` = slot 1 goes in `SET_IN_REF_PIC1`. Ada takes HEVC
  references by list position; ours left REF_PIC1 unset when the reference was in slot 1, which was the fault;
- the history buffer is 768 x CTB columns x (CTB rows + 1/2) bytes (Ada: 768 x CTB columns);
- **no HEVC B pictures** (NVIDIA's own driver refuses `hevc_nvenc -bf`): enc_open turns them off on 0xb4b7.

H.264 (P and B pictures) and 4:4:4 (HEVC Rext and H.264 High 4:4:4 Predictive; a lossless round trip is byte-exact) work
unchanged.

## T15.03: decoders on NVDEC 0xc4b0

Before: HEVC conformance 166/186 and x265 28/33, VP9 vectors 26/29, VP9 4K faulting.

**HEVC, wide pictures.** 3200x1800 and 4K had wrong rows at CTB edges. Turing splits pictures wider than about 3072 into
columns and fills the filter-above and SAO-above areas by width; we sized them by height. Now by the larger dimension.

**HEVC, tiles.** Every stream with at least 3 tile columns and 3 tile rows failed (`TILES_A/B`, `DBLK_D-G_VIXS`; 3x2,
2x3 and 2x2 grids passed): decoding stopped part way with status 0 (green unwritten areas in a staircase along tile edges),
or a few pixels differed at a tile edge. Enlarging one filter area at a time (each 16x), only the SAO-left area mattered.
At 1x it ran into the BSD control area behind it; 5x5 tiles at 1080p need 2x. Now 8x (under 1 MB at 4K). Result: x265
30/33 (the rest 4:2:2 / monochrome) and conformance 178/186, **the same 8 failures as on Ada** (4:2:2, pictures over 8192,
WPP_D, TSUNEQBD, EXT_A).

**HEVC through VideoToolbox.** Comparing with Apple's software decoder showed a few frames differing at random. Against
ffmpeg ours is bit-exact on every run; Apple's software HEVC decoder varies from run to run on the last frames.

**VP9, frame size.** Turing answers status 0x10 for frames 64 pixels or less in either dimension (one superblock row or
column: 8x8 to 64x64, 200x8, 8x200; 66x66 and up are bit-exact; NVIDIA lists 128x128 as VP9's minimum). Buffers sized
for 256x256 and surfaces of 128x128 made no difference. vp9dec refuses such frames on 0xc4b0 and libnvencvt refuses
such sessions, so VideoToolbox can try another decoder.

**VP9, large pictures.** 2048x1088, 1280x1440, 1920x3840 and 4K faulted (no completion, error notifier 0xffff), while
4096x1024 and 640x1440 passed. Enlarging each buffer in turn, only the intra-top buffer mattered. Its class header lacks
`SET_INTRA_TOP_BUF_OFFSET`, but Turing uses it. Filled with a marker, the engine writes W64 x H64 / 128 bytes, 32 per
superblock, at every size (8 and 10-bit). Ada needs a line of about 4 bytes per pixel of width. Now width x 8 x bytes per
sample plus 32 per superblock. HEVC does not touch that buffer on Turing.

**VP9, segmentation maps.** `15-segkey_adpq` and `19-skip` fail. A frame that keeps the previous segmentation map
(`segmentation_update_map` 0) decodes as if segmentation were off:
- the output is identical with either segment buffer as the read buffer, with both filled with segment 0 or with segment
  1, with buffers 64x larger, with `segmentMapTemporalUpdate` set and with `segmentEnabled` 0;
- the errors sit where the map's segments differ from segment 0 (alternate Q: small errors that propagate; the skip
  feature: the engine misparses and answers status 0x5);
- our adapted probabilities match libvpx's on every frame (`vpxdec` built with a dump of its frame context after
  adaptation, `vendor/libvpx` v1.15.2), so the counters are not the cause.

mesa-nova manages the maps the same way and targets Ampere. With the headers only this looks like an engine limit:
vp9dec logs it once per session. Tracing NVIDIA's Linux decoder on this card would show whether its driver works around it,
but that would need the user's approval (only encoder traces were approved).

**AV1.** NVDEC 0xc4b0 and NVENC 6.6 have no AV1. av1dec_open needs NVDEC 0xc7b0 or 0xc9b0, and enc_open needs NVENC 0xc9b7
for AV1. Both now fail at open with a message.

## T15.04: libnvencvt on TU117

The GPU check (PCI device ID from the IORegistry) accepts TU117 (0x1f80-0x1fff) besides Ada (0x2600-0x28ff); the RM
fallback accepts NVENC 0xb4b7. Other Turing and Ampere cards keep NullMoth's encoders. On TU117 the AV1 encoder and decoder
are not registered. When enc_open turns B pictures off (HEVC on NVENC 6.6), the session follows: with 2 B pictures assumed,
HEVC files had 118 decode errors. A second session whose NVENC1 channel cannot be created moves to NVENC0, since the GTX
1650 and the RTX 4060 have one NVENC.

Checks through VideoToolbox (`vtencfile`, `vtdecode`, library injected):
- H.264 and HEVC encode in real-time, fast and quality modes, P-only and with B pictures (H.264); every file decodes
  without errors. On crowd_run / park_joy 1080p, two B pictures beat P-only at a lower rate, as on Ada; on vtencfile's
  synthetic pattern they do not.
- H.264, HEVC, HEVC Main 10, VP9 (4K 179 fps), MPEG-2 and MPEG-4 decode; ours is bit-exact against ffmpeg.

Lesson: vtencfile's last argument is an *output* (it writes the source it encoded). Pass a scratch path there and the clip
in `VT_SRC`. Two runs overwrote `~/vt-streams/natural/crowd60.nv12` and `park1080_60.nv12`; both were restored from the
dev VM's copies in `/root/natural` (SHA-256 checked).

## T15.05: decoder benchmark

`scripts/guest/bench-dec.sh` on the cached crowd_run streams (300 frames), table in benchmarks.md "GTX 1650":
- **H.264:** ours 447 fps at 1080p and 121 at 4K, NullMoth's 154 and 36: 2.9-3.3x, as on the 4090.
- **HEVC:** level, 609 / 574 at 1080p and 183 / 192 at 4K. Main 10 is level too (351 / 349, 94 / 93).
- **VP9:** 580 / 180 fps, only ours.
- **MPEG-2, MPEG-4 Part 2 and VP8:** below ffmpeg's 16-thread software decoders, as on Ada.

The card reaches about 40-65 % of the 4090's rates.
